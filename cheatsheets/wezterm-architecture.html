The object model

Pane, tab, and window

Pane: one terminal session, with its PTY and a shell or application. A foreground editor/build runs inside that session. Focus chooses which pane receives input.

Tab: a collection of panes arranged into a split layout. Each tab has an active pane. Zoom changes the view of one pane; it does not create a different session.

Window: the native OS window displays a mux window's tabs. A window can contain many tabs, and a tab can contain many panes.

A tab index is a position (zero-based in this config); a pane ID is an identifier used by CLI operations. They are not interchangeable.

Close scope and process lifetime

Close paneShuts down that terminal session and its associated process. If it was the last pane, its tab disappears too.
Close tabCloses every pane in that tab. Other tabs remain; closing the last tab removes its window.
Close windowCloses the window's tabs/panes in the normal local setup. Other windows are separate scopes.
Quit applicationExits the GUI application rather than closing only one window. Use the native application Quit action when that is the intention.
Switch workspaceChanges which project's windows are shown. It does not intentionally terminate their sessions.

A separate mux server or remote domain can manage sessions independently of a GUI connection. Those setups have their own detach/persistence behavior. This repository does not configure persistent remote sessions; do not treat a normal local window close as a detach operation.

Window close and application quit are distinct OS actions, particularly on macOS. Whether the application remains after its last window closes depends on the frontend/platform.

Close shortcuts · Step-by-step closing workflow

Confirmation and process exit are separate

Explicit close: pane/tab key actions use confirm = true. Native window close uses window_close_confirmation = 'AlwaysPrompt'. These are separate controls.

Even with confirmation enabled, WezTerm can skip the prompt when it judges the contained process safe to close. skip_close_confirmation_for_processes_named lists process names such as idle shells that may be exempt.

Program exits itself: exit_behavior = 'CloseOnCleanExit' closes cleanly exited processes and retains failed ones for inspection. A retained pane may have no running process.

Confirmations are not file saves or process checkpoints. Save application data before ending the session.

Workspaces group live projects

A named workspace groups mux windows. Its windows contain the usual tabs and panes. Switching the active workspace shows a different group while the other project's processes can continue.

Workspace names organize live state; they do not serialize applications or restore them after reboot. A saved Lua configuration describes preferences and launch actions, not the state of your editor or shell.

Multiple projects can use the same local domain. The workspace name does not select a shell, machine, container, or filesystem.

Domains choose the execution backend

A domain connects panes to an execution backend: local processes, or an optionally configured WSL/SSH/mux connection. Each pane belongs to a domain; workspaces and tab layouts are separate grouping choices.

The shared split/new-tab actions use CurrentPaneDomain, so a new terminal follows the focused pane's domain. A new local pane runs locally; following a remote domain depends on that domain's configuration.

The shared config leaves domain configuration at WezTerm's defaults. It does not set up an SSH server, WSL distribution, or standalone mux service.

Launch profiles describe commands

A launch-menu profile is a command plus arguments (and optionally environment/directory settings). Selecting it starts a terminal program with those inputs; merely listing it does not run it.

A profile is not a saved pane or workspace. The executable, initialization files, and dependencies must exist on the machine/backend where the command executes.

The shared menu offers Windows shell choices only on Windows. Private machine-only launch entries belong in the installed home-directory local config and should check platform/tool availability.

Scrollback is retained terminal output

Each pane has its own output history. The shared config retains 10,000 scrollback lines per pane; once older lines are discarded, scrolling or search cannot recover them. Increasing scrollback_lines retains more future history and uses more memory.

The scrollbar is a view control for the active pane's history, drawn in the window's right-hand padding. It is enabled here with enable_scroll_bar = true; WezTerm's default is to hide it. Hiding it locally does not disable keyboard scrolling.

Full-screen programs such as editors and pagers often use an alternate screen and their own navigation. Their displayed content may not be part of normal terminal scrollback. Scrolling terminal history does not replace the application's own scrolling.

Scrollback is not a durable log or saved session. Use application logging when you need output to survive closing the pane. See the scrolling workflow for reading history and returning to live output.

Configuration files and live state

Git checkoutVersioned shared .wezterm.lua plus a commented, no-op wezterm.local.lua example. No private workstation commands belong here.
Installed shared fileThe active home-directory .wezterm.lua. With copy-based setup, pulling Git does not update this copy automatically.
Optional local filewezterm.local.lua beside the active shared file. Returns a function applied last. Absence is allowed; malformed/unreadable files surface an error.
Live processesRunning shells/editors/builds belong to their terminal sessions. Reloading Lua settings does not restart them or turn their state into a backup.

The loader uses wezterm.config_dir, the active configuration directory. An explicit checkout --config-file loads the public checkout example, not a home-directory private override. See setup for OS paths and migration details.
